# Weekly Aging Report

## Purpose
Generates and sends the recurring Weekly Aging Report, run every Wednesday and Friday right after [weekly-backlog-report](../weekly-backlog-report/). Takes a ServiceNow export already filtered to incidents whose "Updated" date is before a cutoff exactly 2 weeks prior to send day, builds a pivot table filtered to the same roster the backlog report uses, drops it into a fixed Outlook email template, and sends it once the user confirms the draft looks right.

## Trigger
Manually started by the user each Wed/Fri from the Tasks app, after they've exported the raw report from ServiceNow and (via the Run dialog's upload box, or by dropping the file into `input/`) provided it. Same as the backlog report: no browser automation - the ServiceNow login/filter/export step is entirely manual, done by the user in their own browser before the task starts.

## Inputs (live in this folder)
- `input/incident (*).xlsx` - this run's raw ServiceNow export, already filtered by the user to incidents last updated before the cutoff date (exactly 2 weeks / 14 days before send day, so the cutoff always falls on the same weekday - e.g. a Friday send uses a Friday cutoff two weeks back). Same default ServiceNow export filename convention as the backlog report (e.g. `incident (19).xlsx`); the build script picks the most recently modified match.
- Upload and clean-up: Run opens an upload dialog with one required input, the ServiceNow export, saved as `input/incident (1).xlsx` (the build script still uses the newest match of the pattern above). `task.json` has `cleanup: {onComplete: true}`: after a COMPLETED run the Tasks engine deletes this run's `input/` files (dotfiles aside), so upload a fresh file for the next run; `output/`, `reference/`, `templates/` and `config/` are never touched, and a failed or abandoned run keeps its input.
- `reference/last update before_5 August 2026.xlsx` - a fully processed example from a prior run (raw data on `Page 1` + pivot on `Sheet1`). Kept as a reference for the expected pivot layout, not reprocessed as input.
- `templates/Aging Incidents  Last updated before 5th August.msg` - a real, previously-sent example email: fixed To/Cc (identical to the backlog report's), subject pattern `Aging Incidents | Last updated before {ordinal day} {month}` (no year in the subject), intro paragraph, HTML pivot table, and the processed workbook attached. This was sent with the *old* plain blue-header table styling, before the Deloitte x Takeda co-brand was built for the backlog report - per the user, this report's new output should use that same co-branding (see Branding below), not the styling in this .msg.
- `../shared/roster/Names.xlsx` and `../shared/roster/name_matching.py` - the same roster and ServiceNow-name-matching logic the backlog report uses (see [weekly-backlog-report/TASK.md](../weekly-backlog-report/TASK.md#name-matching-servicenow-assigned-to-vs-roster)). Promoted to a workspace-level `shared/roster/` folder once this report needed the identical roster and matching logic, per this workspace's rule against duplicating shared logic across task folders.

## Differences from weekly-backlog-report
- **No aging-logic formulas.** The backlog report adds Today / Aging in Days / Age Bucket columns via formulas; this report doesn't need them because ServiceNow's "Updated" date filter already defines the aging cutoff (the user filters ServiceNow itself before exporting, and the task computes the same cutoff - exactly 2 weeks/14 days before send day - independently for the subject/filename text). It does add one small non-formula helper column, `Updated (Day)` - see Technical notes for why.
- **Same roster filtering as the backlog report.** Both reports restrict their pivot to the same fixed list of people, `../shared/roster/Names.xlsx`. (Note: `reference/last update before_5 August 2026.xlsx`, the one prior-run example on hand, was *not* filtered this way - it shows everyone in the raw data. Confirmed with the user that was a gap in that prior run, not the intended behavior - the pivot shape and formatting still match that reference, just with the roster filter now applied like the backlog report always has.)
- **Different pivot shape.** Backlog is a crosstab (Rows: Priority > Assigned to, Columns: Age Bucket). This report is a 3-level row-only pivot (Rows: Priority > Assigned to > Updated date, single Data field: Count of Number) - matching `reference/last update before_5 August 2026.xlsx` exactly, including its `d-mmm` day/month-only date formatting, and with each date row aggregating a real count of same-day updates (see Technical notes - the first working version of this pivot got that wrong, showing one row per exact timestamp instead).

## Workflow
1. User manually logs into ServiceNow, applies the "Updated before {cutoff}" filter, exports the report as Excel, and drops the file into `input/`.
2. User starts the task (Run in the Tasks app).
3. `scripts/build_report.py` finds the raw export, copies it to `output/last update before_<date>.xlsx`, adds the `Updated (Day)` helper column (see Technical notes), computes the cutoff date (today - 15 days), matches the roster in `../shared/roster/Names.xlsx` against the raw "Assigned to" text (via `../shared/roster/name_matching.py` - same matching the backlog report uses), and writes `output/pivot-input.json` with the cutoff formatted for the subject (`5th August`) and full body sentence (`5th August 2026`), plus the visible raw "Assigned to" values and roster email map.
4. `scripts/create_pivot.ps1` builds a real, native Excel PivotTable via Excel COM (Rows: Priority > Assigned to > `Updated (Day)`; Data: Count of Number), then filters the "Assigned to" field to just the roster-matched names from `pivot-input.json` - same technique as the backlog report's PivotTable filter. No recalculation step is needed first (unlike the backlog report) since there are no formulas in this workbook.
5. `scripts/build_email_data.py` flattens the filtered pivot into `output/email-data.json` (each row tagged `priority` / `name` / `date` / `grand_total` by its indent level), joining each "name" row to its roster email via `pivot-input.json`'s `raw_to_roster` and email mappings without reopening the roster workbook.
6. `scripts/create_draft.ps1` builds the HTML body - same Deloitte x Takeda co-branding as the backlog report - creates the Outlook item with the fixed To/Cc and this report's subject pattern, attaches the workbook, and calls `.Display()` so the draft opens visibly in the user's own Outlook window. It does **not** send.
7. The task pauses at its `review_gate` so the user can look at the draft, then at the `send_gate` confirm gate and waits for explicit confirmation.
8. On confirmation, `scripts/send_draft.ps1 -DraftToken <token>` reopens the uniquely tagged draft from Outlook Drafts and sends it via the user's Outlook desktop app. The token remains valid if Outlook changes the draft's EntryID after the user reviews it. Nothing is sent before the user confirms at the `send_gate`, even after the draft itself was already approved.

## Name resolution
Since the pivot is filtered to the roster, every "name" row should already have a roster email attached (`build_report.py`'s `raw_to_roster` matching + `build_email_data.py`'s email join - same roster and matching logic as the backlog report, including its `KNOWN_ALIASES` for ServiceNow spelling quirks like "Dileepu a" -> "Dileepu Gowda"). Resolution is layered for robustness:
1. `create_draft.ps1` resolves the polished "@Last, First" Exchange display text from the roster email (`Session.CreateRecipient(email).Resolve()`) - the same reliable method the backlog report uses.
2. If a "name" row somehow has no roster email (shouldn't happen once filtering is working, but as a safety net), it falls back to resolving the raw ServiceNow name text directly against the Exchange directory (`Session.CreateRecipient(name).Resolve()`) - confirmed unreliable on its own in an early test (legitimate roster names like "Naga Siva Kumar Nakka" failed this way), which is why it's only a fallback, not the primary path.
3. A name that fails both falls back to plain, non-linked text and is flagged in the script's console output for the user to check before sending.

## Wording (Template library)
The subject, To, Cc and the greeting/message above the table can be changed without touching this folder: in the AI OS **Templates** app, a template ticked for *Aging Report* replaces them (placeholders `{{date_subject}}`, `{{date_full}}`, `{{total}}`, `{{people}}`). `build_email_data.py` asks `shared/template_lib` for the template for the key `task:weekly-aging-report` and writes the result into `email-data.json` (`subject`, `to`, `cc`, `body_html`); `create_draft.ps1` uses `body_html` when present and its own text otherwise, so with no library or no template for this task the draft is unchanged. The table, logos and attachment are not part of a template. See [docs/templates.md](../../docs/templates.md).

## Technical notes
- No browser automation - ServiceNow export is a manual, out-of-band step performed by the user.
- No `Recalc-Workbook.ps1` step - this report's workbook has no formulas to recalculate.
- The pivot table is a real Excel PivotTable built via COM (`scripts/create_pivot.ps1`), same rationale as the backlog report (openpyxl can't reliably create a native, refreshable PivotTable, and the user wants the real thing).
- **Date-row grouping uses a helper column, not Excel's PivotField.Group().** The third pivot row level needs to show one row per *calendar day* with a real count (e.g. "6-Aug | 24"), not one row per exact timestamp (each count 1) - the raw "Updated" values include time-of-day down to the second and are almost never identical between rows. The obvious approach - Excel's native date grouping (`PivotField.LabelRange.Group(...)`) - proved unreliable when driven headlessly via COM in this environment: across several attempts (Periods array with only Days selected, a numeric `By` day-interval, grouping via a single cell vs. the full item range) it kept silently collapsing the *entire* date range into one bucket, or falling back to a coarse auto "Months" grouping, regardless of the interval requested - reproduced even in an isolated minimal test workbook, so it's not specific to this data. `build_report.py` instead adds a plain (non-formula) `Updated (Day)` column - the "Updated" timestamp with time-of-day dropped to midnight - and `create_pivot.ps1` uses that directly as the row field, so identical days collapse into one pivot item on their own, the way any ordinary pivot field would.
- Outlook desktop is controlled via COM automation (not the web app), since the send step must happen in the user's actual desktop Outlook.

## Data handling
Exported ServiceNow data and generated reports are real PMO backlog data. Never commit them anywhere in this workspace - `input/`, `output/`, and `reference/` are for local working files only.
