# Monthly Report Deck

## Purpose
Processes a monthly ServiceNow incident export into the proven monthly trend-analysis workbook, refreshes its current-month native Excel PivotTables and linked charts, and pauses for review. This task's scope ends at the reviewed workbook; updating the PowerPoint deck from it is handled outside this task.

## Inputs
- `input/incident*.xlsx` - the raw ServiceNow export for one calendar month. The newest matching file is used.
- Upload and clean-up: Run opens an upload dialog with one required input, the month's ServiceNow export, saved as `input/incident.xlsx` (matches `incident*.xlsx`; the newest match is still used). `task.json` has `cleanup: {onComplete: true}`: after a COMPLETED run the Tasks engine deletes this run's `input/` files (dotfiles aside); `reference/` (previous monthly workbooks) and `output/` are never touched, and a failed or abandoned run keeps its input.
- Previous monthly workbooks (`Monthly Incidents Trend Analysis - *.xlsx`) in `reference/` and `output/` - the classification knowledge base. `prepare_data.py` discovers all of them (month read from `Trend analysis!A1`), and the newest one before the report month becomes the structural template. `output/` holds the user-reviewed deliverables and outranks `reference/` for the same month, so always leave the final corrected workbook in `output/`.
- `reference/incident-June2026-chitra.xlsx` - June classification reference.
- `reference/monthly trend notes (updated).docx` - business notes for trend categorization.

All inputs and outputs contain real operational data and are intentionally ignored by Git.

## Current Workflow
1. `scripts/prepare_data.py` validates that the raw export has the required 17 columns and unique incident numbers. The latest `Opened` month is the report month; older tickets are expected because the ServiceNow export includes tickets opened, resolved, or closed in that month. It deliberately loads the workbook in normal mode because this ServiceNow export has incorrect worksheet dimension metadata (`A1`) despite containing thousands of rows.
2. The script maps the raw columns into the July workbook's 20-column `Incidents` model. All 17 ServiceNow fields are copied unchanged; the three helper fields are `Org`, `AG2`, and `Subcategory2`.
3. `Org` is derived from `../shared/roster/Names.xlsx` through the shared name matcher: matched names and blank assignees are Deloitte; unmatched named assignees are Non-Deloitte. `AG2` is the system an incident is ABOUT: proven per-number classifications from previous months win; otherwise the `Configuration item` decides (built-in system rules such as `(DPS)` -> DPS or `Lookback Notification System 2.0` -> LNS 2.0, then CI mappings learned from history); the `Assignment group` is only the routing queue and serves as the final fallback before flagging for review. `Subcategory2` preserves proven per-number classifications (newest month wins), with conservative inference only for new incidents. Per the trend notes, state placeholders take precedence over every other classification and come ONLY from the current month's `State`: Cancelled incidents are always `Cancelled`, and On Hold / In Progress incidents are always `WIP`. Placeholders are never learned or inherited: a Closed/Resolved incident whose history only offers WIP/Cancelled is re-inferred, and if nothing applies it goes to the review queue.

   Classification look-back: knowledge comes from ALL previous monthly workbooks, not just the template. When the newest workbook can't classify an incident, earlier months (July, August, September, ... when building October) often can; on conflict the newest month wins.
4. The script writes `output/prepared-incidents.xlsx` with `Incidents`, static names-only `Org`, and `Review Needed` sheets. Every review row includes a `Review reason` identifying the unresolved helper field. It also writes `output/report-data.json` with metrics and paths, and `output/review-incidents.json` — the review queue (per-incident classifying fields + the Subcategory2 option vocabulary) that powers the in-app review feature.

   **Local AI suggestions** (`scripts/ai_classify.py`, run at the end of this step): for incidents the rules above left as `Needs Review`, the local Ollama model suggests a Subcategory2 from the Short description, Resolution notes and the trend-notes rules, grounded in the most similar tickets already classified in the previous monthly workbooks (TF-IDF nearest neighbours, shown to the model as examples; the label list is the history-proven vocabulary, so one-off typos are never offered). The model first writes what it understood the incident to be about (`issue`), then picks the label, so the label follows from understanding rather than keyword matching. The suggestion (label, `issue`, confidence, evidence, `is_new`) is stored on the queue entry as `ai_suggestion`; it is only a suggestion — the human still confirms it, and it can never override a rule-based classification or produce a WIP/Cancelled placeholder. Confidence is the model's own rating capped by history evidence (a label no similar ticket used is never `high`; a brand-new label is always `low`). Identical tickets are classified once and answers are cached in `output/ai-suggestions-cache.json`. The step is never fatal: if Ollama is down, no model is installed, or the time budget runs out, the queue is left as is and the review works exactly as before. Ticket text is only ever sent to a loopback Ollama (a non-local `OLLAMA_BASE_URL` is refused). Settings (all optional env vars): `MONTHLY_AI_SUGGEST=0` switches it off, `MONTHLY_AI_MODEL` / `OLLAMA_MODEL` pin a model (otherwise `qwen3.5:4b`, then `gemma4:12b`, `llama3.2` - measured on real September tickets, the 4B model was as accurate as the 12B one and 2.5x faster), `MONTHLY_AI_BUDGET_SECONDS` (default 1200) caps the time spent. **Speed:** Ollama ignores an integrated GPU (e.g. the Radeon 780M) unless `OLLAMA_IGPU_ENABLE=1` is set in the environment Ollama starts in (restart Ollama after setting it); measured on this laptop that makes prompt reading about 4x and generation about 2x faster (about 6 s per ticket instead of 14 s with the 4B model).
5. The task pauses at the `review_incidents` gate. In the Tasks app, the user opens the review queue and works through it with the fast review flow: picking a category saves it immediately (autosaved) and jumps to the next unresolved incident; Enter picks the top search match (or the AI suggestion when the search box is empty); a category that isn't in the list is added by typing it (`+ Add "…" as a new category`) and then appears in the list for the rest of the run and, because it lands in the workbook's `Subcategory2`, in every later month's list; "Also apply to N other pending incidents with the same description or almost the same resolution notes" resolves them at once (the engine marks incidents whose notes are ~85% the same text with a `notes_group`; notes copied from a parent incident only group when the descriptions are alike too, and notes with different `Sub-Category` tags never group; the AI classifies such a group once); "Accept AI suggestions" fills in every pending suggestion (or only the high-confidence ones). Resolutions are saved to `output/review-resolutions.json`, and the gate refuses to pass while any incident is still unclassified.
6. `scripts/refresh_workbook.ps1` first folds the resolutions into the staging workbook via `scripts/apply_resolutions.py` (updating both `Incidents` and `Review Needed` in place), then copies the proper workbook to `output/`, transfers values with Excel's native values-only paste so long text and reference formatting are preserved, installs the static Org lookup and review queue, and repoints only PivotTables backed by the local `Incidents` sheet. Historical pivots backed by prior workbooks or SharePoint are left untouched. It builds a hidden Deloitte-intake source (Deloitte tickets opened in the report month) for the application, priority, and `Trend analysis` pivots. On `Trend analysis` it PRESERVES the previous month: the prior current-month block (and its summary table) is frozen to static values before columns shift, a fresh intake pivot block is inserted at the far left (WIP and Cancelled stay visible so the block reconciles with Deloitte intake), the static `Total incidents` cell is rewritten to the Deloitte intake count, and the top-9 summary table (placeholders excluded, % over Deloitte intake) plus its `% of Occurence` chart are rebuilt and repointed.
7. The task pauses at `review_workbook` so the user can inspect the generated workbook before its values are used in a deck.

## Month Roll
This phase refreshes one month's raw export against the prior month's analysis workbook. `prepare_data.py` picks the newest previous monthly workbook as the template, so months are always processed in order; a template more than one month behind the export (or newer than it) is rejected so history is not skipped or overwritten. `scripts/refresh_workbook.ps1` rolls the workbook forward non-destructively: the previous month's `Trend analysis` block is frozen to values (its summary table first, since it can hold GETPIVOTDATA formulas that need the live pivot), three columns are inserted at the left, and the new month is built there - a fresh pivot on `Subcategory2` (all values visible), the month stamp, the static total, and the top-9 summary table with its chart. The new month is also appended to the `Charts` month table and the Intake/Resolved/Backlog trend charts are extended to include the new row. Re-running a month re-rolls from the previous month's workbook and overwrites the month's output file, keeping runs idempotent. Historical pivots backed by prior workbooks or SharePoint are left untouched.

## Output Metrics
`report-data.json` records Deloitte intake (Deloitte tickets opened in the report month), Resolved (Deloitte tickets currently in `Closed`, `Resolved`, or `Cancelled`, retained as the `closed_or_resolved` compatibility field), in-progress count, on-hold count, backlog (Deloitte `In Progress + On Hold` tickets), state counts, and review count. The Excel step updates the matching row in the `Charts` month table with intake, Resolved, and backlog. The application, priority, and Trend analysis charts use Deloitte intake data; the Resolved metric uses terminal-state Deloitte tickets from the full export.

## Incident knowledge repository
`scripts/build_knowledge.py` reads every monthly trend-analysis workbook of the year (January's Top Trending workbook through the latest `Monthly Incidents Trend Analysis`, including June's `incident-June2026-chitra.xlsx`) and writes a local repository to `reference/knowledge/` (ignored by Git, never packaged — it holds real ticket text):

- `incidents-YYYY-MM.jsonl` — one proven classification per ticket (short description, resolution notes, the extracted `Sub-Category` tag, category, state, assignment group, the team's label and its canonical spelling; the newest month's label wins when a ticket appears in several months; WIP/Cancelled placeholders are not knowledge).
- `category-guide.json` — per category: ticket count, per-month counts, every spelling used, typical descriptions, typical tags and distinctive keywords.
- `conflicts.json` — descriptions the team classified in more than one way, and the resulting ceiling for any classifier that only sees the description (77.7% on the 2026 data — the resolution notes and the month's convention decide the rest).
- `knowledge.json` — manifest and label statistics. `eval-YYYY-MM.json` — written by the evaluator.

Rebuild after each month's workbook is final: `python scripts/build_knowledge.py --source "C:/path/to/2026"` (the `SOURCES` table in the script maps each month to its workbook and sheet). `prepare_data.py` uses the repository for every previous month that has no workbook in `reference/` or `output/` (newest month still wins on conflict), and the local AI gets the category guide in its prompt.

`python scripts/evaluate_ai.py --month 2026-10 [--limit N] [--model M] [--base-url http://127.0.0.1:11434]` replays a past month from the months before it (rules first, then the AI on what the rules leave open) and reports accuracy per stage, so any prompt/model/repository change can be judged by numbers. Measured on the 2026 data (trained on the months before): the rules classify about 98.6% of a month's new tickets and are 99.1-99.3% correct on those; the 1.4% they cannot classify (80-120 tickets a month, mostly the team's judgement calls such as `Other` vs `Hardware Issue`) are what the AI suggests for and the human confirms.

## Category spelling variants
One category used to appear several times in the options because people typed it differently (`Soft Goods Issue`, `softgoods issue`, `softgood issue`, `soft good isse`). `scripts/labels.py` folds such variants into the most used spelling: case, spacing, punctuation, a plural "s" and a one-character typo (two from 20 characters) are ignored; digits must match (`CMS 1.0` ≠ `CMS 2.0`); labels under 12 characters must match exactly (`EDQ Issue` ≠ `EOD Issue`); the first letter must match; a typo may not introduce a word another category really uses (`Referral issue` ≠ `Deferral issue`); and adding a whole word (`… Arm Used PIN`) makes a different category. It is applied (1) when history is learned, so the review options, the learned mappings, the AI's label list and examples list each category once, (2) to a typo'd `Sub-Category` tag in the resolution notes, (3) in the repository (`category-guide.json`), (4) in the review panel (`labelMatch.ts`, the TypeScript twin, tested with the same cases): typing a variant offers "Use existing …" instead of adding a duplicate, Enter uses the existing spelling, imports and "Accept AI suggestions" do the same, and (5) in `apply_resolutions.py`, so a label saved in another spelling lands as the category the workbook already uses. Genuinely different categories that only look alike (`Physical Issue` / `Physical related issue`, `Donor Reaction issue` / `Donor Reaction record issue`) are left alone: merge those by adding an alias to `SUBCATEGORY_ALIASES` in `prepare_data.py`.
